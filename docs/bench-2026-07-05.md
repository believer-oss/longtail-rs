# Longtail pure-Rust port — benchmark report (2026-07-05)

> **Purpose.** This document records NUMBERS and DECISION RECORDS — it is not a
> compat gate. A bad result here is a *finding*, never a license to tune code in
> this stage. The four verdicts (micro parity vs C, e2e vs golongtail,
> owned-struct revisit, FastCDC go/no-go) are in §7; the tables that back them
> are in §3–§6.

## 2. Methodology (fairness rules, all binding)

### 2.1 Micro-benches (criterion, `harness = false`)

`support/longtail-bench/benches/{chunker,hash,compression,index_codec}.rs`.
Rust-vs-C pairs run **in the same bench binary** via the `differential` feature
(C through `longtail-ffi`: `ChunkerAPI::chunk_streaming`, `HashAPI::hash_buffer`,
`CompressionRegistry::{compress,decompress}_buffer`). Inputs are generated
in-memory from a seeded ChaCha20 stream (bigger than any committed fixture, so
steady-state dominates). Throughput (MiB/s) is criterion's `Throughput::Bytes`.

### 2.2 E2E harness (`support/longtail-bench/src/bin/e2e.rs`)

Not criterion — a bespoke harness. **Every timed run is a fresh spawned child
process for all three implementations** (Rust `longtail` CLI, C via the
`ffi-driver` bin, spawned golongtail v0.4.5). Each child is measured with
`libc::wait4` on its exact pid, which returns *that child's* rusage —
`ru_maxrss` (KiB→MiB, the peak RSS) and `ru_utime + ru_stime` (the CPU). This is
mandatory: `RUSAGE_SELF` is a process-lifetime cumulative max and
`RUSAGE_CHILDREN.ru_maxrss` is a running max across *all* reaped children, so
both cross-contaminate an in-process measurement.

- **All drivers `--release`.**
- **Worker parity**: every impl pinned to the same worker count per run
  (golongtail `--worker-count N`, ffi-driver `--worker-count N`, Rust CLI
  `--worker-count N`). Default N=8; the **cold** scenario sweeps {2, 4, 8, 32}
  (NumCPU=32) — the ffi requires ≥2 (single-worker bikeshed deadlock).
- **Page-cache policy — pre-warm**: the store is read into the OS page cache
  once before all timed runs and caches are never dropped, so every
  implementation reads a warm store. This isolates implementation differences
  from cold-disk latency (the recommended policy).
- **Store-index resolution parity**: no `--version-local-store-index-path` is
  passed, so all three resolve blocks via the store's canonical `store.lsi`
  (the fs optimistic path). Uniform, and cheap because upsync wrote it.
- **Per-run hard timeout + retry (the ffi watchdog)**: the C
  `get_existing_store_index_sync` missed-wake race can hang a run (the
  download-path audit caught it hanging 35+ min; it also tripped during
  upload-path work). Every timed run has a
  hard timeout = `5 × baseline` (a measured single downsync), floored at 60 s. A
  timed-out run is SIGKILLed, recorded as a timeout (never averaged in; note the
  reported timeout counter reflects FINAL-attempt failures only — an intermediate
  timeout recovered by the bounded retry appears in stderr, not the counter, so
  gating consumers should capture stderr), and
  retried up to 3× with a *fresh process* — the process-granularity form of
  testkit's in-thread watchdog (`downsync_three_way.rs`); a fresh process = fresh
  C job/cond-var state, which is exactly what recovers the missed wake.

### 2.3 Dataset (`~1 GiB synthetic`, new parametric generators)

The committed fixtures (29 MiB) are far too small for e2e numbers. The harness
generates a **synthetic ~1 GiB source** via new seeded-ChaCha20 generators
(`longtail_bench::{dataset_plan, write_dataset, write_churned_v2}` — new code;
testkit's `random_bytes`/`compressible_text` are private and fixed-size, left
untouched) and upsyncs it into a temp fs store via the **pinned golongtail
binary** (worker-count 16 — byte-determinism is irrelevant here). Every
implementation downloads the *same* golongtail-produced store — no upload-path
dependency.

- **File sizing**: a mix of large (≤256 MiB — the cap so RSS measures the
  pipeline, not one giant buffer), medium (1–16 MiB), and small (4–64 KiB)
  assets, ~55/35/10 % of the byte budget, split between incompressible (random)
  and compressible (word-like text). See the run's printed layout in §4.
- **v1→v2 churn (~10 %)** MUST include mid-file content shifts, not just
  whole-file ops — otherwise CDC shows nothing. The generator applies, per
  touched file, one of: in-place modify (same-length region overwrite),
  **shifting insert** (splice bytes mid-file → all following chunks shift),
  **mid-file delete** (drop a region → content shifts back), append; plus a
  whole-file add and a whole-file delete. The actual tally is in §4.

**Scenarios**: cold (empty target, no block cache, warm page cache),
warm-cache (a pre-populated `.lrb` block cache), incremental (target already at
v1, downsync v2). All bench artifacts live under `target/bench/` (git-ignored);
targets are deleted between runs to hold the disk budget (~5–6 GiB peak: two
source versions + store + one target + one cache).

### 2.4 Reproduce


## 3. Micro-bench results (chunker, hash, compression)

All cells are criterion medians (100 samples except the compression cells noted),
`--features differential,fastcdc`, `bench` profile. Throughput is criterion's
`Throughput::Bytes`. "Rust÷C" is the throughput ratio; a value > 1 means Rust is
faster. Cells outside ±10% are flagged **⚑**.

### 3.1 Chunker (HPCDC-Rust vs HPCDC-C vs FastCDC; 64 MiB buffers)

| target | input | HPCDC-Rust | HPCDC-C | FastCDC | Rust÷C (HPCDC) |
|---|---|---|---|---|---|
| 32768 | incompressible | 1.103 GiB/s | 1.067 GiB/s | 3.133 GiB/s | 1.03 |
| 32768 | compressible | 1.104 GiB/s | 1.067 GiB/s | 3.139 GiB/s | 1.03 |
| 131072 | incompressible | 1.111 GiB/s | 1.070 GiB/s | 3.187 GiB/s | 1.04 |
| 131072 | compressible | 1.113 GiB/s | 1.070 GiB/s | 3.195 GiB/s | 1.04 |

The compat-critical HPCDC chunker: **pure-Rust is 3–4 % *faster* than the C
library** on every cell (both are the same gear-hash rolling algorithm; the Rust
inner loop optimizes at least as well). FastCDC is ~2.85× HPCDC throughput —
noted for verdict 4, but see §6 for why the throughput edge does not translate to
a dedup win.

### 3.2 Hash (blake3 / blake2s, Rust vs C; chunk-sized buffers)

| size | blake3-Rust | blake3-C | Rust÷C | blake2s-Rust | blake2s-C | Rust÷C |
|---|---|---|---|---|---|---|
| 4 KiB | 2.285 GiB/s | 2.262 GiB/s | 1.01 | 973.4 MiB/s | 963.7 MiB/s | 1.01 |
| 64 KiB | 3.718 GiB/s | 3.721 GiB/s | 1.00 | 981.0 MiB/s | 963.0 MiB/s | 1.02 |
| 1 MiB | 3.742 GiB/s | 3.765 GiB/s | 0.99 | 978.3 MiB/s | 963.7 MiB/s | 1.02 |

blake3 is at dead parity (both sides are SIMD blake3, ±1 %); blake2s-Rust is
1–2 % faster. **Every cell within ±10 %.** blake3 is the production default hash
for the port.

### 3.3 Compression (per codec × {compress, decompress}, Rust vs C; 8 MiB payloads)

Encode byte-parity is a deliberate **non-gate** (block identity = hash of the
chunk-hash array, not the compressed bytes), so decompress uses Rust-produced
frames as the common valid input for both sides. Compress cells are 10 samples,
decompress 20 (brotli q11 of 8 MiB is intentionally slow); ratios, not absolute
CI numbers, are the point.

| codec | op | payload | Rust | C | Rust÷C |
|---|---|---|---|---|---|
| zstd_default | compress | compressible | 720.7 MiB/s | 701.2 MiB/s | 1.03 |
| zstd_default | decompress | compressible | 1.828 GiB/s | 1.760 GiB/s | 1.04 |
| zstd_default | compress | incompressible | 6.751 GiB/s | 5.892 GiB/s | **1.15 ⚑** |
| zstd_default | decompress | incompressible | 31.45 GiB/s | 18.81 GiB/s | **1.67 ⚑** |
| zstd_max | compress | compressible | 3.013 MiB/s | 3.031 MiB/s | 0.99 |
| zstd_max | decompress | compressible | 2.963 GiB/s | 2.817 GiB/s | 1.05 |
| zstd_max | compress | incompressible | 13.92 MiB/s | 14.01 MiB/s | 0.99 |
| zstd_max | decompress | incompressible | 30.40 GiB/s | 18.69 GiB/s | **1.63 ⚑** |
| lz4 | compress | compressible | 968.4 MiB/s | 1.053 GiB/s | **0.90 ⚑** |
| lz4 | decompress | compressible | 3.369 GiB/s | 3.603 GiB/s | 0.94 |
| lz4 | compress | incompressible | 4.486 GiB/s | 16.48 GiB/s | **0.27 ⚑** |
| lz4 | decompress | incompressible | 18.82 GiB/s | 18.90 GiB/s | 1.00 |
| brotli_default | compress | compressible | 886.8 KiB/s | 976.3 KiB/s | 0.91 |
| brotli_default | decompress | compressible | 1.284 GiB/s | 1.816 GiB/s | **0.71 ⚑** |
| brotli_default | compress | incompressible | 1.938 MiB/s | 2.165 MiB/s | **0.90 ⚑** |
| brotli_default | decompress | incompressible | 12.19 GiB/s | 10.58 GiB/s | **1.15 ⚑** |

Reading: **zstd — the production codec — is at parity-or-better everywhere**, with
a large Rust win on incompressible decode (1.6–1.7×; the Rust `zstd` decoder
short-circuits stored/raw frames faster). The flagged losses are all in codecs
longtail rarely writes:
- **lz4 compress of incompressible input is 3.7× slower in Rust** (`lz4_flex`
  lacks the C `LZ4_compress` "acceleration"/early-abort fast path that C uses when
  no matches are found). lz4 compressible compress is −10 %.
- **brotli decompress compressible is −29 %** (the pure-Rust `brotli` decoder is
  slower than the C reference); brotli compress is ~−10 %.

None of these is a compat concern (compressed bytes are not gated) and none is on
the production (zstd) path; they are recorded as findings and roadmap inputs, not
regressions to block on. See verdict 1 (§7).

## 4. E2E results (fs-local; three implementations × three scenarios)

Synthetic dataset produced by the harness (§2.3) and upsynced once by golongtail:
**v1 = 384.0 MiB / 22 files, v2 (churn) = 136.0 MiB, store = 125.5 MiB**. Every
timed run is a fresh child, `wait4`-measured; median of n=5; store page-cache
pre-warmed; per-run hard timeout 60 s (5× the 0.1 s golongtail baseline, floored
at 60 s); **0 timeouts across the whole matrix**. Worker sweep pins *both*
`--worker-count` and `--remote-worker-count` to N on the Rust and go legs (the ffi
driver has a single unified worker count).

| cold | rust | 4 | 5 | 0 | 442 | 525 | 169 |

| cold | go | 4 | 5 | 0 | 141 | 540 | 111 |

| cold | ffi | 8 | 5 | 0 | 141 | 806 | 126 |
| cold | go | 8 | 5 | 0 | 141 | 773 | 151 |
| cold | rust | 32 | 5 | 0 | 422 | 698 | 170 |
| cold | ffi | 32 | 5 | 0 | 181 | 1396 | 340 |
| cold | go | 32 | 5 | 0 | 221 | 1458 | 366 |
| warm | rust | 8 | 5 | 0 | 442 | 429 | 47 |
| warm | ffi | 8 | 5 | 0 | 141 | 734 | 130 |

Reading:
- **Rust wall is flat at ~420–460 ms across every worker count on both planes and
  across all three scenarios.** That is the signature of a serial bottleneck, not
  a concurrency-tunable one: sweeping workers {2,4,8,32} does not move Rust's wall,
  while golongtail/ffi (~140–220 ms, ≈3× faster) grow only their CPU and RSS with
  worker count (I/O-bound, fs store on a warm page cache saturating quickly). This
  quantifies an open question from the download-path work — the apply/block-fetch pipeline is
  effectively serial after preflight.
- **Incremental costs Rust the same ~460 ms as a full cold download** even though
  only ~10 % of bytes changed, and its RSS (276 MiB) is the highest of any cell —
  the target scan reads+chunks whole assets, so the single 256 MiB asset is held in
  memory (another download-path open question). golongtail/ffi incremental is 141 ms / ≤64
  MiB.

### 4.1 The 1 GiB scale ceiling (three-way, recorded separately)

The e2e matrix runs at **384 MiB, below the 512 MiB prefetch budget**, because the
pure-Rust cold download **deadlocks** on any working set above that ceiling
(§ headline finding; `remote.rs` `preflight_get` acquires a byte-denominated
permit for *every* required block before any is consumed, so `acquire_many_owned`
blocks forever once Σ block sizes pass `DEFAULT_MAX_PREFETCH_BYTES`). At 1 GiB
(direct three-way, `--worker-count 8`), inherited from the prior run and confirmed
by the harness watchdog:

| impl | wall | peak RSS | result |
|---|---|---|---|
| golongtail v0.4.5 | 0.29 s | 190 MiB | ✅ wrote 1.0 GiB |
| C via ffi-driver | 0.20 s | 156 MiB | ✅ wrote 1.0 GiB |
| **Rust CLI** | **>60 s (killed by watchdog)** | — | ❌ **deadlock, 0 bytes** (gdb: all tokio workers parked) |

This is a **finding, not fixed by this benchmarking**; it is the top follow-up
recommendation and the reason the comparison matrix is capped at 384 MiB.

## 5. Index-codec results (owned-struct revisit trigger)

Parse + serialize of the largest committed `.lvi`/`.lsi` and a deliberately
over-scale synthetic index (~30× a realistic game index). Criterion medians;
throughput via `Throughput::Bytes`; round-trip asserted byte-identical.

| index | size | parse | serialize | parse+ser |
|---|---|---|---|---|
| version_index (committed `zoo.lvi`) | 196 KiB | 7.65 µs (24.4 GiB/s) | 16.75 µs (11.2 GiB/s) | 24.4 µs |
| store_index (committed `store.lsi`) | 67 KiB | 2.43 µs (26.3 GiB/s) | 5.58 µs (11.5 GiB/s) | 8.0 µs |
| version_index (synthetic 100k assets / 500k chunks) | ~15 MiB | 3.68 ms (4.07 GiB/s) | 1.51 ms (9.95 GiB/s) | 5.2 ms |
| store_index (synthetic 50k blocks / 500k chunks) | ~6.5 MiB | 282 µs (23.1 GiB/s) | 623 µs (10.5 GiB/s) | 0.9 ms |

The owned-struct codecs run at **4–26 GiB/s** — faster than any I/O the download
path performs. At realistic scale (committed indexes; the bench store's own
`v1.lvi` is 494 KiB) parse+serialize is **tens of microseconds**, i.e. ~0.02 % of
even the fastest e2e downsync wall (140 ms). Even the over-scale synthetic
version index (15 MiB, ~30× a real game manifest) round-trips in 5.2 ms — still
never the bottleneck. Backs verdict 3 (§7): **keep owned structs.**

## 6. HPCDC vs FastCDC — throughput and dedup

Throughput is from §3.1 (FastCDC ~2.85× HPCDC). Dedup is measured by the `dedup`
driver over the synthetic v1→v2 chain at target 32768 (chunk key = blake3 longtail
hash of the chunk content). **The chunk-size distribution is reported alongside
the ratio deliberately** — without it the ratio is meaningless, since a smaller
average chunk trivially dedups better.

| algo | chunks (v1) | mean (B) | median (B) | v1 self-dedup | v2 self-dedup | download-avoided (v2∩v1 / v2) |
|---|---|---|---|---|---|---|
| HPCDC | 24 621 | 16 354 | 12 673 | 100.0 % | 100.0 % | **94.0 %** |
| FastCDC | 20 295 | 19 840 | 18 857 | 100.0 % | 100.0 % | **94.0 %** |

Fixture chain (tiny; most files < min chunk, single-chunk): both algorithms 7
chunks, download-avoided 67.0 % (identical).

Reading: FastCDC produces **~18 % fewer, larger chunks** (20 295 vs 24 621; mean
19.8 KiB vs 16.4 KiB) — so any dedup ratio it posts is against a coarser grid. The
**directional download-avoided fraction is identical at 94.0 %** on realistic
churn (mid-file inserts/deletes + modify + append + whole-file add/delete). So
FastCDC's only measurable edge is a smaller chunk count (marginally smaller index
/ per-chunk overhead) and higher raw throughput — with **no dedup advantage**.
Backs verdict 4 (§7).

## 7. Verdicts

### Verdict 1 — Micro parity vs C: **PASS on all compat-critical paths (within ±10 %; Rust often faster)**

The paths that carry compat obligations — the HPCDC chunker (block identity), the
hash (blake3/blake2s), and the index codecs (byte-identical `.lvi`/`.lsi`) — are
**all within ±10 %, and Rust is at parity or faster** on every one (HPCDC +3–4 %,
blake3 ≈0 %, blake2s +1–2 %, index codecs 4–26 GiB/s). The only cells outside
±10 % are in compression, which is an explicit non-gate (compressed bytes are not
part of block identity): Rust wins big on zstd incompressible decode (1.6–1.7×)
and loses on lz4 incompressible compress (0.27×, an `lz4_flex` fast-path gap) and
brotli decompress (0.71×). zstd — the production codec — is parity-or-better
throughout. Verdict: **PASS**; the compression outliers are recorded as findings,
not compat failures.

### Verdict 2 — E2E vs golongtail: **FAIL on fs-local** (slower and a hard scale ceiling)

Two distinct failures, both findings (benchmarking does not tune product code):
1. **Scale ceiling / deadlock (headline):** the pure-Rust cold download deadlocks
   above the 512 MiB prefetch budget (§4.1). golongtail and C/ffi download 1 GiB
   in ~0.2–0.3 s; Rust never completes. Release-blocking for the launcher (games
   are multi-GB).
2. **Below parity even under the ceiling:** at 384 MiB, Rust cold wall (~420 ms)
   is ~3× golongtail/ffi (~140 ms) and **does not scale with worker count** (flat
   across {2,4,8,32} on both planes) — a serial post-preflight pipeline.
   Incremental is *also* ~3× and RSS-heavy (whole-asset target scan).

Scoped to **fs-local**; the "async I/O plane wins on cold S3-like workloads"
hypothesis is **not** adjudicated here (§2.2 has no minio run) — recorded as an
open question. Parity threshold (agreed): Rust median wall ≤ 1.1× golongtail on
the same cell; Rust is ~3× on every cell, so **FAIL**.

### Verdict 3 — Owned-struct revisit: **KEEP owned structs** (parse/serialize is not a hot spot)

Agreed threshold: revisit zero-copy only if index parse+serialize ≥ 1 % of a
realistic e2e downsync wall. Measured (§5): realistic indexes round-trip in tens
of microseconds (~0.02 % of a 140 ms downsync), at 4–26 GiB/s — faster than the
I/O they feed. Even a ~30× over-scale synthetic index stays at single-digit ms.
**Well under the 1 % threshold → keep the owned-struct `.lvi`/`.lsi` codecs;** do
not spend complexity on zero-copy views. (The `crates/longtail-core/src/lib.rs`
PERF doc-comment is updated to cite this result — the one authorized product-code
touch in this stage.)

### Verdict 4 — FastCDC go/no-go: **NO-GO** (throughput win, zero dedup win, would orphan every store)

Agreed threshold: go only if FastCDC is *materially* better on **both** throughput
**and** dedup **and** a store migration is justified. Measured: FastCDC has a real
throughput edge (~2.85× HPCDC, §3.1) but **no dedup advantage** — the directional
download-avoided fraction is identical at 94.0 % (§6), and FastCDC gets there with
~18 % *fewer, coarser* chunks. FastCDC has **no compat obligation**, and switching
would **orphan every existing store's dedup** (block identity is the HPCDC chunk
boundary). A throughput-only win does not justify a store migration → **NO-GO;
keep HPCDC.** FastCDC stays a benchmarking-only feature.

## 9. ADDENDUM (2026-07-06) — post-fix re-measurement

> **Measurement-precision note (post-audit)**: the harness's wait4 loop polls at a
> 20 ms tick, so reported walls are quantized up to the next tick — "1.00×" cells
> mean "same 20 ms bucket" (up to ~12% ambiguity at 161 ms). An independent
> unquantized re-measurement (blocking wait, min-of-7, both planes pinned N=8,
> alternating legs) puts the 1 GiB cold cell at go 267.9 ms / rust 273.7 ms =
> **1.022×** — genuine parity on a shared I/O floor (rust burns ~12% more CPU at
> the same wall). Worst-case under adversarial quantization: 1 GiB ≤ 1.08×
> (inside the 1.1× parity definition); 384 MiB ≤ 1.14× (inside the 1.25× hard
> gate). A future harness touch could drop the poll to 1-2 ms.

> Everything above (§1–§8) is the baseline record and is left
> untouched. This section re-runs the affected e2e cells AFTER the
> download-path fixes (see docs/rust-port.md): Fix 1 removes the preflight
> budget deadlock (budget gates background prefetch only; demand fetches
> bypass), Fix 2 makes the block apply concurrent (bounded to the resolved
> remote worker count) and removes two write-path syscall/memcpy costs. Same
> machine (§1), same harness and methodology (§2.2), medians of n=5, both
> worker planes pinned, per-run hard timeout 60 s, stderr captured on every
> run (no watchdog retries occurred). Ambient load during these runs ≈1.6–2.9
> (comparable to the baseline re-run pass). The §8 note that the 384 MiB cap
> is "mandatory" no longer applies — 1 GiB now completes (below).
