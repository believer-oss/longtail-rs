## Findings

### `ALG-01` — Windows per-PR lane runs 3 of the 8 documented compat gates

**P1** · `hardening` · CONFIRMED · `COMPAT-RISK`

- **Where:** `crates/longtail/tests/lvi_byte_gate.rs:7`, `crates/longtail/tests/upsync_byte_gate.rs:21`,
  `crates/longtail/tests/{smoke,downsync_e2e,deadlock_regression}.rs`,
  `crates/longtail-cli/tests/commands_spec.rs:10` — all `#![cfg(unix)]`.
- **What:** every integration test in `crates/longtail` and `crates/longtail-cli` compiles to
  nothing on Windows. `.github/workflows/rust.yaml:38-53` runs the same `cargo test` on
  `windows-latest`, so the Windows lane is green while executing **no** byte gate, **no**
  end-to-end downsync, **no** upsync, and **no** CLI test. Mapping `docs/rust-port.md`'s eight
  gates (`docs/rust-port.md:87-96`) onto what actually runs:

  | Gate | Test | Per-PR Linux | Per-PR Windows |
  |---|---|:--:|:--:|
  | ① fixture round-trip | `format_golden.rs` | yes | yes |
  | ② boundaries == C streaming | `chunker_golden.rs` | yes | yes |
  | ③ hashes == C | `hash_differential.rs` | **weekly** | **weekly** |
  | ④ every `.lsb` decodes + verifies | `hash_recompute_golden.rs` | yes | yes |
  | ⑤ downsync → golongtail's tree | `downsync_e2e.rs` | yes | **no** |
  | ⑥ Rust↔Go upsync interop | `upsync_interop.rs` | **weekly** | **weekly** |
  | ⑦ `.lvi` byte-identical | `lvi_byte_gate.rs` | yes | **no** |
  | ⑧ concurrent Rust+Go shards | `s3-minio.yaml` | **scheduled** | **scheduled** |

  Windows: ①②④. Linux: ①②④⑤⑦.
- **Failure scenario:** a Windows-only regression in the scan/permission/path layer ships. Concrete:
  `FileInfos::from_scanned_entries` sorts on `relative_path.as_bytes()`; a change that let a
  backslash reach `relative_path` on Windows (`\` = 0x5C vs `/` = 0x2F) reorders assets, changing
  `m_NameData`, `m_NameOffsets`, and every asset's chunk mapping — a total `.lvi` incompatibility.
  Nothing in the Windows per-PR lane looks at a `.lvi` built from a folder scan. The Tauri download
  path is the primary Windows consumer.
- **Evidence:** the `#![cfg(unix)]` lines above; `.github/workflows/rust.yaml:38-56`;
  `docs/rust-port.md:87-96`.
- **Recommendation:** the `.lvi` byte gate genuinely cannot pass cross-platform — `m_Permissions`
  differs by design (`docs/format-spec.md` §7) — so do not try to run it verbatim. Two cheap steps
  that close most of the hole:
  1. Split `lvi_byte_gate` into a permission-independent comparison (every array except
     `permissions`, plus the total byte length) that runs everywhere, and the full-bytes assertion
     that stays unix-only. A path/sort/chunking/hashing regression then fails on Windows too.
  2. Make `downsync_e2e` and `commands_spec` run on Windows with
     `TreeManifest::compare(.., mask_mode = true)` — the helper already supports mode masking
     (`support/longtail-testkit/src/tree_manifest.rs:91`), and `TreeEntry` carries `blake3_hex`, so
     content is still fully checked.
- **Tradeoff / risk:** more Windows CI minutes (R8 owns the budget); `corpus.rs` generation is
  documented Linux-only for permissions (`corpus.rs:10-12`) but its *content* generation is
  platform-independent, so the corpus itself is usable.
- **Effort:** M
- **Regression test to add:** the two variants above; plus a Windows-lane assertion that at least
  one `.lvi`-producing test actually ran (a `#[test]` that fails if the permission-independent gate
  compiled out).

### `ALG-02` — `decode_block_payload` sizes its allocation from an untrusted frame header, and brotli decode is unbounded

**P1** · `memory` · CONFIRMED (brotli) / PLAUSIBLE (lz4, zstd)

- **Where:** `crates/longtail-core/src/compress.rs:292-320` (header parse) and `:238-244`
  (`Brotli::decompress`).
- **What:** `uncompressed_size` is read straight out of the block payload
  (`compress.rs:302-303`) and handed to the codec as an allocation size with no upper bound. For
  brotli this is explicit and unbounded on both ends: `Vec::with_capacity(uncompressed_size)` at
  `:239`, then `brotli::BrotliDecompress(&mut reader, &mut out)` at `:241` which grows `out` to
  whatever the stream decodes to. The length check that would catch a lie happens at `:314`,
  **after** the memory has been committed.
- **Failure scenario:** a `.lsb` in the store — corrupted in transit, truncated by a failed upload,
  or hostile — carries `tag = 0x62746c31` (brotli default) and a header declaring
  `uncompressed_size = 0xFFFF_FFFF`. `Brotli::decompress` immediately requests a 4 GiB `Vec`. On the
  Tauri desktop path this is an allocation failure, which in Rust **aborts the process** — the app
  dies with no error surface instead of reporting `DecodedLengthMismatch`. Worse, a legitimate-looking
  small `uncompressed_size` with a brotli bomb payload (brotli's window makes ~1000:1 trivial) grows
  `out` past the declared size until the machine OOMs; `:314` is never reached. With the download
  path fetching blocks concurrently, N workers multiply it.
- **Evidence:** `compress.rs:292-320`; `compress.rs:238-244`; the decorator that calls it on every
  remote read is `crates/longtail-store/src/compress.rs:74`, wired in by
  `crates/longtail-store/src/uri.rs:158`, i.e. on by default for every store URI. I grepped for any
  layer that bounds the value and found none: `crates/longtail-core/src/block.rs:129-138` explicitly
  keeps the payload as "everything after the block-index region" without a length check, and no
  `Σ chunk_sizes` comparison exists anywhere in `longtail-core`/`longtail-store`/`longtail` (see
  ALG-03).
- **Recommendation:** pass the known bound in. `decode_stored_block`
  (`compress.rs:350-352`) already holds the `BlockIndex`, so compute
  `expected = Σ block_index.chunk_sizes` and (a) reject `uncompressed_size != expected` before
  resolving the codec, and (b) give `decode_block_payload` an explicit `max_uncompressed: usize`
  parameter that brotli enforces by decompressing into a `Take`-style limited sink rather than an
  unbounded `Vec`. Both are typed-error paths, not panics. C's decoder is *less* strict here, but
  this only changes which malformed inputs are **rejected**, never which well-formed bytes are
  accepted — a C-written block always has `uncompressed_size == Σ chunk_sizes`.
- **Tradeoff / risk:** `COMPAT-RISK` in the narrow sense that it tightens read acceptance. The gate
  that would catch over-tightening is
  `support/longtail-testkit/tests/hash_recompute_golden.rs:161` (per-PR: every committed `.lsb`
  decodes to exactly `Σ chunk_sizes` with verifying chunk hashes) — which is precisely the invariant
  being asserted, so a correct implementation cannot fail it.
- **Effort:** S for (a), M for (b).
- **Regression test to add:** extend `crates/longtail-core/tests/codec_malformed.rs` with a
  brotli-tagged frame whose declared `uncompressed_size` is `u32::MAX` and assert a typed error is
  returned without a large allocation (e.g. via a counting allocator in the test binary), plus a
  small-declared/large-actual brotli bomb case.

### `ALG-03` — nothing validates a decoded payload against `Σ chunk_sizes`, though the doc comment says it does

**P2** · `hardening` · CONFIRMED

- **Where:** `crates/longtail-core/src/compress.rs:346-352`.
- **What:** the doc comment reads "The result has length `Σ chunk_sizes` (verified by
  [`decode_block_payload`] against the frame's `uncompressed_size` for compressed blocks)."
  `decode_block_payload` compares `decoded.len()` against the frame's *own* declared
  `uncompressed_size` (`compress.rs:314`) — it never sees `chunk_sizes`. The stated invariant is
  therefore unverified, and for `tag == 0` the payload is returned verbatim with no length check at
  all (`compress.rs:293-295`).
- **Failure scenario:** an uncompressed (`tag == 0`) `.lsb` whose payload is 100 bytes short of
  `Σ chunk_sizes` is accepted by the codec layer; the consumer that slices chunk ranges out of it
  either panics on an out-of-range slice or silently reads a short final chunk. Either way the
  failure surfaces far from the cause, as a panic or a wrong chunk hash, rather than as a typed
  "block truncated" error at the boundary that knows both numbers.
- **Evidence:** `compress.rs:293-295`, `:314`, `:346-352`; the grep for a `Σ chunk_sizes` check
  returned only three unrelated sites (`crates/longtail/src/inspect.rs:109`,
  `crates/longtail/src/upsync.rs:236`, `crates/longtail-store/src/remote.rs:787`) — none on the
  decode path.
- **Recommendation:** implement the check the comment already promises, in
  `decode_stored_block`, for both `tag == 0` and `tag != 0`. Same fix vehicle as ALG-02(a).
- **Tradeoff / risk:** `COMPAT-RISK` (tightens reads); same gate as ALG-02.
- **Effort:** S
- **Regression test to add:** a `tag == 0` `StoredBlock` with a payload one byte short of
  `Σ chunk_sizes` must produce a typed error.

### `ALG-04` — zero-valued chunk/block parameters are accepted where C returns `EINVAL`

**P2** · `hardening` · CONFIRMED

- **Where:** `crates/longtail-core/src/build.rs:39` (`max_hash_size.max(1)`),
  `crates/longtail/src/version.rs:105` (same clamp on the streaming path),
  `crates/longtail-core/src/pack.rs:78` (`max_chunks_per_block.max(1)`) and `:80`
  (`size_limit` from `max_block_size`).
- **What:** C validates all three and refuses: `LONGTAIL_FATAL_ASSERT(ctx, target_chunk_size != 0,
  return EINVAL)` (`longtail.c:2391`), `LONGTAIL_VALIDATE_INPUT(ctx, chunk_count == 0 ||
  max_block_size != 0, return EINVAL)` and the same for `max_chunks_per_block`
  (`longtail.c:6769-6770`). The port turns each into a degenerate-but-successful run. The CLI
  applies no validation either — `crates/longtail-cli/src/main.rs:718-720` copies the flags through
  with no `value_parser` range.
- **Failure scenario:** `--target-chunk-size 0` in a CI script. `HpcdcChunker::from_target(0)`
  returns a valid `(48, 48, 48)` chunker; `max_hash_size` becomes `0`, is clamped to `1`, and
  `asset_part_count = 1 + size/1 = size + 1`. Every byte becomes its own range, hence its own chunk:
  a 1 GiB asset yields ~10⁹ one-byte chunks, ~10⁹ blake3 calls, ~10⁹ one-byte `read_exact` calls,
  and `.lvi` arrays of ~24 GB — an OOM after hours of CPU, where golongtail exits immediately with
  `EINVAL`. `--target-block-size 0` gives `size_limit = 0`, so the greedy fill takes exactly one
  chunk per block: a 300k-chunk upload becomes 300k `.lsb` objects and 300k S3 PUTs (a real money
  cost, and a store shape no C writer produces).
- **Evidence:** `build.rs:39`; `version.rs:105`; `pack.rs:78,80`; `longtail.c:2391`,
  `longtail.c:6769-6770`; absence of validation at `crates/longtail-cli/src/main.rs:240-244,718-720`.
- **Recommendation:** reject at the `longtail-core` boundary, where the C precondition lives:
  `chunk_asset`/`create_version_index` return an error for `target_chunk_size == 0` (or
  `max_hash_size == 0`), and `create_store_index` returns `FormatError` for
  `max_block_size == 0 || max_chunks_per_block == 0` instead of clamping. `create_store_index`
  already returns `Result`. Then delete the two `.max(1)` clamps and the `.max(1)` in `pack.rs:78`,
  which exist only to paper over the missing validation.
- **Tradeoff / risk:** no compat risk — these inputs cannot occur in any store C produced, and
  refusing them matches C exactly. Also add them to `docs/rust-port.md` §"Deliberate divergences"
  if the decision is to keep accepting them.
- **Effort:** S
- **Regression test to add:** in `crates/longtail-core/tests/build_diff.rs`, assert
  `create_version_index(.., target = 0, ..)` and `create_store_index(.., max_block_size = 0, ..)` /
  `(.., max_chunks_per_block = 0, ..)` all error. Miri-safe.

### `ALG-05` — the fixture-integrity gate has no test proving it can fail

**P2** · `hardening` · CONFIRMED

- **Where:** `support/longtail-testkit/src/fixture_manifest.rs:98-130` (`Manifest::verify`).
- **What:** `cargo run -p xtask -- verify-fixtures` is the only per-PR check that the committed
  fixtures on disk are the bytes the manifest says they are — it runs on **both** OS lanes
  (`.github/workflows/rust.yaml:34,54`) and is the reason the whole golden strategy is trustworthy.
  Its logic is correct as written (extra file, missing file, sha mismatch, size mismatch are all
  reported). But no test anywhere constructs a mismatching pair and asserts `verify` reports it.
- **Failure scenario:** a refactor introduces an early `return problems;` above the loop, or changes
  `list_fixture_files`' skip list so it skips everything, or flips
  `expected.remove(rel.as_str())`'s `None`/`Some` handling. `verify-fixtures` then prints
  "OK: 112 files" (or "OK: 0 files") on both lanes forever, and a tampered or accidentally-rewritten
  fixture — the thing that makes every downstream golden self-fulfilling — goes unnoticed. This is
  the highest-leverage silent failure in the test tree: it disarms gates ①②④⑤⑦ at once.
- **Evidence:** `fixture_manifest.rs:98-130`; `15-coverage/summary.txt` reports the file at
  **8.20% region / 7.04% line**, and the zero-count `DA:` records in `15-coverage/lcov.info` cover
  lines 49-51 and 56-130 — i.e. everything except `sha256_hex`. Note this number is largely a
  *measurement* artifact: `verify` runs inside the `xtask` binary, not under `cargo test`, so
  `cargo llvm-cov` cannot see it. The real gap is the missing failure-path test, not that the code
  never runs.
- **Recommendation:** three `#[test]`s in `fixture_manifest.rs`, over a `tempfile` dir with two
  small files: (a) a correct manifest verifies with zero problems, (b) flipping one byte of one file
  yields exactly one `sha256 mismatch` problem, (c) deleting a file and adding an unlisted file
  yields exactly one `missing` and one `extra` problem. Roughly 40 lines, no fixtures, runs on both
  lanes and under miri.
- **Tradeoff / risk:** none.
- **Effort:** S
- **Regression test to add:** as above. Related: `Manifest::load` (`:91-94`) uses
  `.expect("parse manifest.json")` inside a function returning `io::Result` — a malformed manifest
  panics rather than erroring; fold that into the same change.

### `ALG-06` — the per-PR boundary golden bypasses the production parameter derivation

**P2** · `hardening` · CONFIRMED · `COMPAT-RISK`

- **Where:** `support/longtail-testkit/src/boundary.rs:54-60`
  (`chunker_params_for_target`), consumed by
  `support/longtail-testkit/tests/chunker_golden.rs:35-41` and
  `support/longtail-testkit/src/differential.rs:69`.
- **What:** the testkit keeps its own copy of `min = max(48, t/8)`, `avg = max(48, t/2)`,
  `max = max(48, t*2)` and then constructs the chunker with the explicit
  `HpcdcChunker::new(min, avg, max)`. So gate ② — the per-PR proof that the pure chunker reproduces
  C's boundaries — never exercises `HpcdcChunker::from_target`
  (`crates/longtail-core/src/chunker.rs:252-258`), which is the function production actually calls
  (`crates/longtail/src/version.rs:41`). Nothing asserts the two derivations agree.
- **Failure scenario:** someone "simplifies" `from_target` — e.g. `target / 8` → `target >> 3` is
  fine, but `min = target / 8` without the `max(48, …)` clamp, or `avg` and `min` transposed — and
  every boundary in production moves while `chunker_golden` stays green because it supplies
  `(min, avg, max)` itself. The remaining net is the hardcoded unit test
  `params_derivation_matches_spec` (`chunker.rs:436-447`), which does catch the clamp and the
  transposition — but it pins only targets `32768`, `1024`, `1`, and not `131072` or `1048576`,
  which are the targets the boundary tables actually use. A derivation bug that only bites at
  `t ≥ 131072` passes both.
- **Evidence:** `boundary.rs:54-60`; `chunker_golden.rs:35-41`; `chunker.rs:252-258`, `:436-447`;
  `15-coverage/summary.txt` puts `boundary.rs` at 81.82% region with the uncovered `DA:` lines being
  41-43 (`to_json`).
- **Recommendation:** delete the duplicate. `chunker_params_for_target` is already
  `pub` on `longtail-core`'s side as `HpcdcChunker::from_target(t).params()`; have `boundary.rs`
  call it (the testkit already depends on `longtail-core`). If a separate copy is wanted so that the
  golden is independent of the code under test — a legitimate position — then add the one
  assertion that makes the independence meaningful:

### `ALG-08` — `per_asset` ↔ `file_infos` alignment rests on a sort duplicated across two crates

- **Where:** `crates/longtail/src/version.rs:37-39` and

### `ALG-09` — `create_missing_content` emits duplicate chunk hashes where C dedups

**P2** · `hardening` · CONFIRMED

- **Where:** `crates/longtail-core/src/pack.rs:148-155`.
- **What:** the port iterates `version_index.chunk_hashes` and pushes every not-yet-stored entry.
  C's path is `DiffHashes` (`longtail.c:6620`), which sorts + `MakeUnique`s both sides before
  differencing, so `added_hashes` is a **set**; a duplicate in the version index collapses to one
  entry, whose size and tag come from `LookupTable_Put`'s last-wins index

  (`pack.rs:132-135`: "A version index's chunk arrays are already deduplicated") — which is true for
  any index this codebase builds — but the function does not enforce it, and
  `StoreIndex::from_block_indexes` does not reject duplicate chunk hashes either
  (`crates/longtail-core/src/store_index.rs:407-442`; it validates only that each block's two
  parallel arrays agree in length).
- **Failure scenario:** `clone-store` reads a `.lvi` it did not build
  (`crates/longtail/src/clonestore.rs:169`) and feeds it to `create_missing_content`. A `.lvi` with a
  repeated chunk hash — corrupt, hand-edited, or produced by some other writer — yields a store index
  in which the same chunk hash appears in two different blocks. Both blocks get written (duplicate
  bytes uploaded), and readers resolving that chunk pick whichever block the index lookup lands on.
  C would have produced one block.
- **Evidence:** `pack.rs:148-155`; `longtail.c:6620-6741`, `:6966-6975`;
  `store_index.rs:407-442`; `crates/longtail/src/clonestore.rs:169`.
- **Recommendation:** dedup defensively in `create_missing_content` — a `HashSet<u64>` guard in the
  loop, taking the **last** occurrence's size/tag to match C's `LookupTable_Put`. Two lines. (The
  alternative — rejecting duplicate chunk hashes in the `VersionIndex` reader — is R1's call and
  changes read acceptance.)
- **Tradeoff / risk:** `COMPAT-RISK`; gate is
  `support/longtail-testkit/tests/packing_differential.rs` (**weekly**) plus
  `crates/longtail/tests/upsync_byte_gate.rs` (per-PR, unix) — neither exercises a duplicate-bearing
  index, so **no existing test would catch a mistake here**. That is itself the finding.
- **Effort:** S
- **Regression test to add:** in `crates/longtail-core/tests/build_diff.rs`, hand-build a
  `VersionIndex` with a duplicated `chunk_hashes` entry and assert `create_missing_content` produces
  a store index whose `chunk_hashes` are unique.

## Named deliverable — the sys/ffi oracle-retirement memo

### What the oracle actually is, mechanically

Before comparing options, four facts that the existing docs get wrong or omit, all verified above.

1. **No `crates/*` coupling at all.** Zero references to `longtail-ffi`/`longtail-sys` in `crates/`.
   The only consumers are `support/longtail-testkit` (feature `differential` →
   `dep:longtail-ffi`, `dep:longtail`, `dep:cc`) and `support/longtail-bench` (feature
   `differential` → `dep:longtail-ffi`). `xtask` forwards the feature. Deleting the pair is a
   `support/` + CI + docs change, nothing more. (ALG-DOC-08.)
2. **The oracle is `v0.3.3-101-g96241fe`, not `v0.4.3`.** `default = ["vendored"]` means the C is
   compiled from the submodule; the `v0.4.3` URL and four SHA256 pins are dead on the default path.
   The fixtures, by contrast, come from **golongtail v0.4.5**. (ALG-10.)
3. **Its requirements are a submodule fetch, a host C toolchain, and libclang** — not a
   SHA256-pinned download. `build.rs:71-76` shells `git submodule update --init longtail` against
   `https://github.com/DanEngelbrecht/longtail` (`.gitmodules` carries the URL; the commit pin is
   the gitlink). `vendored()` then compiles with `-maes -mssse3 -msse4.1` (or MSVC `/arch:AVX`) and
   the aarch64 arm is commented "untested, probably wrong" — so the oracle is x86-64 only.
4. **The per-PR value of the oracle is exactly 28 JSON files.** The committed boundary tables are
   the only fixtures with `produced_by: "ffi chunker (C)"`, and they are already *committed data* —
   deleting the crates does not invalidate them. What deletion removes is the ability to
   **regenerate** or **drift-check** them, because `xtask gen-fixtures` and `diff-fixtures` are
   `#[cfg(feature = "differential")]` in their entirety (`xtask/src/main.rs:834-836` is the
   `bail!("diff-fixtures requires --features differential")` stub).

Gates ⑥ and ⑧ survive deletion because they drive the **golongtail binary**, not the FFI
(`upsync_interop.rs`, `s3-minio.yaml`). Gate ③ is the only *conformance* casualty: the frozen
blake3/blake2 KATs in `crates/longtail-core/src/hash.rs:136-139` lose their anchor to C and become
self-referential constants. That anchor is cheap to replace — both algorithms have published RFC/spec
test vectors, and the mapping to a longtail `u64` is 8 bytes little-endian, so a KAT against the
upstream BLAKE2s/BLAKE3 official vectors is a strictly *better* anchor than our own C build.

The honest summary: **deletion costs the fixture-regeneration capability and one replaceable
conformance anchor. It costs zero per-PR byte-compat coverage.**

### Option A — drop entirely

| | |
|---|---|
| **Gains** | Deletes two crates, a 500+-line `build.rs`, the submodule, and the C-toolchain/libclang requirement. Removes the differential CI lanes and the `--workspace` cold-build cost (price: R8). Removes the x86-64-only constraint on CI. `cargo build --workspace` becomes equal to `cargo build`, so `01b-clippy-ws.txt`'s cold-path hazard disappears. |
| **Costs** | `fixtures/` becomes **permanently frozen**: no `gen-fixtures`, no `diff-fixtures`, no way to extend the boundary grid or add a corpus case. Any future need for a new golden must be met by hand or by writing new tooling. Gate ③ loses its C anchor. The `fixture-freshness.yaml` scheduled job becomes a no-op. |
| **Irreversibility** | High in practice. Restoring means re-adding a submodule pointing at a repo that may have moved, re-fixing a `build.rs` that already carries a dead download path and an "untested, probably wrong" aarch64 arm, and reproducing a bindgen setup against `bindgen 0.72`. |

### Option B — retain as conformance / performance oracle

| | |
|---|---|
| **Gains** | Keeps `gen-fixtures`/`diff-fixtures`, i.e. keeps `fixtures/` a living artifact that can be extended and drift-checked against upstream. Keeps the weekly cross-implementation conformance suite (format parse/write equivalence over 300 generated indexes per shape, packing/prune byte-identity, exhaustive discriminator equality over `avg ∈ [48, 9_309_387]`, three-way downsync). ### What differential fuzzing can and cannot replace

`cargo-fuzz` is installed and there are **no** fuzz targets (`MANIFEST.md`, and `fuzz/` does not
exist). Three targets are worth building; the first is the one that substitutes for real oracle
coverage.

**Target 1 — `chunker_range_equivalence` (the valuable one).** Property: the reader-driven
range-split path and the whole-slice path must produce identical `(chunk_hash, size)` lists.
This is the claim `crates/longtail/src/version.rs:86-97` makes in prose, that
`crates/longtail-core/src/build.rs:7-8` calls byte-gate-critical, and that no test checks with
arbitrary part boundaries (ALG-11).

```rust
// fuzz/fuzz_targets/chunker_range_equivalence.rs
#[derive(arbitrary::Arbitrary, Debug)]
struct In { target_log2: u8, mhs_shift: u8, data: Vec<u8> }
fuzz_target!(|i: In| {
    let target = 1u32 << (10 + (i.target_log2 % 11));          // 1 KiB .. 1 MiB
    let Ok(ck) = HpcdcChunker::from_target(target) else { return };
    let mhs = 1u64 << (6 + (i.mhs_shift % 14));                // 64 B .. 512 KiB: forces many parts
    let whole = chunk_asset(&i.data, &ck, mhs, &Blake3);
    let streamed = chunk_asset_streaming(&mut Cursor::new(&i.data),
                                        i.data.len() as u64, &ck, mhs, &Blake3).unwrap();
    assert_eq!(whole, streamed);
    // structural invariants
    let total: u64 = whole.iter().map(|(_, s)| *s as u64).sum();
    assert_eq!(total, i.data.len() as u64);
    assert!(whole.iter().all(|(_, s)| *s <= ck.params().2));
});
```
Needs `chunk_asset_streaming` made `pub` (or the target placed in `crates/longtail`). A deliberately
small `mhs` is the point: it makes every input cross many range seams, which the real 32 MiB value
never does in a test.

**Target 2 — `chunker_seed_mode_agreement`.** A genuine oracle with no C involved, from a property I
proved while reviewing: each seed byte `w_i` enters the hash rotated by `(47-i)` and is evicted on
roll `i+1`, by which point the whole-hash rotations have advanced it to `(47-i)+(i+1) = 48 ≡ 16
(mod 32)` — exactly cancelled by `GEAR[out].rotate_left(16)`. So the two seed modes converge after
48 rolls, and when `min == 48` (any `target ≤ 391`) they must be **bit-identical** for all inputs.
Assert that; assert also that they agree on every boundary at or beyond `min + 48` within a scope
whose first `min` bytes they agreed on. This pins the exact §6 divergence window (`(min, min+47]`)
without the C library.

**Target 3 — `payload_framing`.** `decode_block_payload(tag, bytes)` must never panic and never
allocate more than the ALG-02 bound, over arbitrary `(tag, bytes)` with tags drawn from the §4
table plus family-prefix neighbours. `crates/longtail-core/tests/codec_malformed.rs:128` already
proptests no-panic over random bytes; coverage-guided fuzzing reaches *valid-prefix* brotli/zstd
frames that random generation never will, which is precisely where ALG-02 lives.

**What fuzzing cannot replace.** It cannot produce a new golden. Every target above checks the port
against *itself* or against a proved invariant; none can tell you what C would have written for a
new corpus case or a new target size. So fuzzing substitutes for the *weekly conformance* value of
the oracle, and not at all for the *fixture-generation* value. That asymmetry decides the
recommendation.

### Recommendation — Option B, with a dated exit and three decoupling steps

**Retain**, because the one thing deletion destroys — the ability to regenerate and drift-check
`fixtures/` — is the foundation the entire per-PR gate stands on, and it is the one capability
fuzzing cannot supply. But retain it as a *deprecated* dependency with a written exit condition,
and spend the release cycle removing the reason it is load-bearing. Note the priority inversion the
evidence exposes: the trustworthy oracle is the **golongtail v0.4.5 binary** (a 60 MB
SHA256-pinned download, no toolchain, produces 78 of 112 fixtures), while the *fragile* oracle is
the FFI library, pinned two minor versions behind, needed for only 28 JSON files. Decoupling means
moving those 28 files onto the good oracle.

Mechanical step list, in order:

1. **Fix the documentation that makes the current state unreadable** — ALG-DOC-01 (CLAUDE.md's
   build path), ALG-DOC-03 (gate cadence/OS), ALG-10 (pin the submodule version visibly). Do this
   first; every later decision depends on people knowing which C is the oracle. *(S)*
2. **Resolve the version skew.** Either bump the submodule to the `v0.4.3` tag or delete
   `upstream_dist()` and its four SHA256 constants. Then run
   `cargo run -p xtask --features differential -- diff-fixtures` and confirm the 28 boundary tables
   still reproduce. That run is also the check on whether v0.3.3→v0.4.3 changed the chunker. *(M)*
3. **Move boundary-table generation off the FFI.** A single-file `.lvi` produced by golongtail
   already contains the ordered per-asset chunk list: offsets are the prefix sums of
   `chunk_sizes[asset_chunk_indexes[start..start+count]]` and the hashes are recorded verbatim. So
   `boundary_table_streaming(input, target)` can be derived from `golongtail upsync` output with no
   C linkage — this is exactly what `self_validation.rs:236` already does in the other direction to
   anchor the tables. Reimplement `xtask`'s boundary step that way and `gen-fixtures` needs only the
   pinned binary. Two caveats: inputs must stay below `max_hash_size` so the range split does not
   interfere (`chunker.input` is 1 MiB, all corpus cases ≤ 9 MiB, all fine at
   `target ≥ 32768`; the `t1024` tables need care since `mhs` is then 1 MiB), and the buffer-mode
   tables need `golongtail --enable-file-mapping` to actually take effect — see Experiment 2, since
   at `96241fe` the flag is ignored (ALG-DOC-04). If the experiment says buffer mode is
   unreachable in released builds, **delete `SeedMode::Buffer` and the 14 `*.buffer.json` tables**
   instead of porting their generation, which removes the last FFI-only fixture dependency
   outright. *(L)*
4. **Re-anchor gate ③ without C.** Replace the four frozen KAT constants in
   `crates/longtail-core/src/hash.rs:136-139` with (or add alongside) assertions against the
   official BLAKE2s and BLAKE3 published test vectors, mapped through the documented
   "first 8 digest bytes, little-endian" rule. Then `hash_differential.rs` is redundant rather than
   load-bearing. *(S)*
5. **Land the three fuzz targets** above, and wire target 1 into CI as a short bounded run
   (`cargo fuzz run … -- -max_total_time=60`) so the range-split equivalence is checked every PR on
   both OSes. *(M)*
6. **Close the Windows hole** (ALG-01) and add the cheap gate-integrity assertions (ALG-05, ALG-07,
   ALG-12, ALG-13). These are what actually protect the switchover, and they are all S-sized. *(M
   in aggregate)*
7. **Then set the exit condition and write it into `docs/rust-port.md`:** once steps 3-5 are done,
   `gen-fixtures`/`diff-fixtures` no longer need the FFI, so delete `support/longtail-sys`,
   `support/longtail-ffi`, the `.gitmodules` entry and submodule, `longtail-testkit`'s
   `differential` feature (with `src/differential.rs`, `build.rs`'s `cc` block,
   `shim/hpcdc_discriminator_shim.c`, and the 9 differential tests), `longtail-bench`'s
   `differential` feature and `src/bin/ffi_driver.rs`, `xtask`'s `differential` feature, and the
   differential CI lanes — and fix the seven prose citations (ALG-DOC-08). Deletion at that point is
   a mechanical change with no coverage cost. *(M)*

If the switchover date forces a choice **now**, between deleting today and keeping today: **keep**.
The crates are not default members, they cost nothing per PR, and the one-line risk of keeping them
(a stale submodule) is far smaller than losing the ability to ever regenerate a fixture.

## Verified good

Do not re-derive these. Each was checked line-by-line against the C in
`support/longtail-sys/longtail/`, not against `docs/format-spec.md`.

- **The 256-entry gear table** (`chunker.rs:45-110`) is identical to `hashTable[]`
  (`longtail_hpcdcchunker.c:22-95`), value for value, in order.
- **The seed loop** (`chunker.rs:352-363`): `min - 48` start, `rot = (48-i-1) & 31`,
  `hash ^= GEAR[b].rotate_left(rot)`, ring seeded in order — identical to `:266-278`. The `& 31` is
  compat-required (without it, seeds for `i < 16` change).
- **The roll step** (`chunker.rs:376-378`): `rotate_left(1) ^ GEAR[out].rotate_left(16) ^ GEAR[in]`,
  with **16** being the constant `ChunkerWindowSize & 31` and not the loop position — identical to
  `:292-295`. This is the subtlest thing in the file and it is right.
- **The boundary test** (`chunker.rs:379`): `hash % d == d - 1`, evaluated *after* `pos` is
  incremented so the triggering byte is inside the chunk — identical to `:297-300`.
- **The tail rule** (`chunker.rs:336-344`): `left <= min` emits everything with no hashing —
  identical to `:255-263`, same `<=` sense.
- **The `max` cap** (`chunker.rs:348`): `data_len = left.min(max)` — identical to `:284`.
- **`SeedMode::Buffer`** (`chunker.rs:354`) matches `HPCDCChunker_NextChunkFromBuffer` (`:452-521`)
  exactly, including its own `buffer_size <= min` tail rule and `max` cap.
- **`rotl32` at `r == 0`**: the C macro `((x << r) | (x >> (32-r)))` is UB at `r == 0`, which the
  seed loop *does* hit (`i = 47` and `i = 15` both give `(47-i) & 31 == 0`). Every realisation —
  x86/ARM shift masking, MSVC `_rotl`, and even a compiler that folds `x >> 32` to 0 — yields `x`,
  which equals Rust's well-defined `rotate_left(0)`. The port is safe *and* strictly better defined.
- **`discriminator_from_avg`** (`chunker.rs:242-245`) reproduces
  `(uint32_t)(avg / (-1.42888852e-7*avg + 1.33237515))` with the same literals, the same operator
  association, `f64` throughout, computed once per instance. Rust performs no automatic FMA
  contraction, and the differential shim disables it on the C side (`build.rs:26-29`), so the two
  cannot diverge via fusion. The golden `d` table (`chunker.rs:419-434`) pins four values.
- **Whole-slice == C streaming.** The port chunks a whole slice where C runs a feeder. This is
  boundary-identical, and the reason is stronger than "the refill buffer is an I/O detail": C's
  `FeedChunker` (`:182-215`) calls the feeder **once**, so a short read *would* produce a spurious
  `left <= min` tail chunk mid-file — but the only feeder,
  `StorageChunkFeederFunc` (`longtail.c:1923-1958`), reads exactly `min(requested, remaining)` and
  errors otherwise. It never short-reads, so `left <= min` occurs only at true EOF. Verified.
- **The range split** (`build.rs:39-59`) is identical to `ChunkAssets` (`longtail.c:2396,2432-2437`)
  plus `DynamicChunking`'s `m_SizeRange == 0` early return (`:2016-2019`): same `u64` arithmetic,
  same zero-range skip, and `saturating_sub` is provably equivalent to C's plain unsigned subtraction
  because `part ≤ ⌊size/mhs⌋ ⇒ part·mhs ≤ size`. C's `hash_size <= chunker_min_size` shortcut
  (`:2051`, with `chunker_min_size = 48`) is correctly subsumed by the chunker's own `left <= min`
  rule, as `build.rs:29-32` claims.
- **BLAKE2s is parameterized, not truncated** — `Blake2sVar::new(8)` matches
  `blake2s(out, sizeof(uint64_t), data, len, 0, 0)` (`longtail_blake2.c:111`) and
  `blake2s_init(state, sizeof(uint64_t))` (`:43`): unkeyed, `digest_length = 8` in the parameter
  block. `hash.rs:165-180` proves it differs from a truncated 32-byte digest. **Correct compat
  semantic.**
- **BLAKE3** — C does `blake3_hasher_finalize(&hasher, (uint8_t*)out_hash, sizeof(uint64_t))`
  (`longtail_blake3.c:100`), i.e. 8 XOF bytes into a native-endian `u64`; on x86 that is the LE
  interpretation of the first 8 digest bytes, which is what `hash.rs:93-99` computes.
- **`unique_hash_indexes`** (`pack.rs:38-52`) matches `GetUniqueHashes` (`longtail.c:4307-4345`)
  exactly: first-occurrence *position*, last-occurrence *index*.
- **The greedy block fill** (`pack.rs:87-121`) matches `Longtail_CreateStoreIndex`'s loop
  (`longtail.c:6801-6860`) condition for condition and in order: tag change, then
  `chunk_count == max_chunks_per_block`, then `current_size + next > max_block_size +
  max_block_size/10`, with the first chunk always taken.
- **`create_missing_content`** (`pack.rs:136-169`) is equivalent to
  `Longtail_CreateMissingContent` + `DiffHashes` (`longtail.c:6882-6990`, `:6620-6741`) **given
  the deduped-input precondition**, including the reorder-to-version-order step. See ALG-09 for the
  precondition and ALG-DOC-05 for the upstream bug it hides.
- **`diff.rs` is exact.** Two independent `if`s for content and permissions (not `else if`) —
  matching `longtail.c:7639-7660`; `SortPathShortToLong` = length asc then index asc
  (`:7345-7382`) and `SortPathLongToShort` = length desc then index desc (`:7384-7422`), both
  reproduced at `diff.rs:106-113`; `path_lengths` uses `strlen`-equivalent lengths including a
  directory's trailing `/`; `get_required_chunk_hashes` matches
  `Longtail_GetRequiredChunkHashes` (`:4349-4418`) including the added-then-modified order and
  first-occurrence dedup. Both comparators are strict total orders, so Rust's stable `sort_by` and
  C's `qsort` produce identical output. `diff.rs` is at **100%** region and line coverage.
- **Parallel chunking cannot perturb output order** (`version.rs:53-74`): `par_iter().map().collect::<Result<Vec<_>,_>>()`
  preserves index order by construction, and `assemble_version_index` consumes `per_asset`
  positionally. The only ordering risk is the `entries` ↔ `file_infos` alignment, which is ALG-08.
- **`hash_util.rs`** mirrors `longtail_core::hash::hasher`'s three-state behaviour exactly, and the
  `hash_identifier_for_name` mapping matches `hashIdentifierMap` (`remotestore.go:474-478`).
- **`compress.rs` framing** matches `compressblockstore.c:135-136` (`[uncompressed u32][compressed
  u32][bytes]`), with `tag == 0` a true passthrough and no header, and the codec resolved before the
  header is read (mirroring `DecompressBlock`). `hash.rs` and `diff.rs` are at 100% coverage;
  `pack.rs` 98.97%, `build.rs` 99.28%, `chunker.rs` 97.81%.
- **The corpus does exercise the range split** against a real oracle: at `target = 1024`
  (`mhs = 1 MiB`) `zoo_medium` contains `repetitive.bin` (2 MiB → 3 parts, last empty) and
  `big-stream` (exactly 1 MiB → 2 parts, second empty), and the `chunk-1024` cell is byte-gated
  against golongtail output. ALG-11 is about making that explicit, not about it being absent.
- **Fixture provenance is genuine.** 78 of 112 committed files come from the pinned golongtail
  v0.4.5 binary (68 `upsync`, 5 `put`, 5 sharded — the last mislabeled, ALG-DOC-07), 28 from the C
  chunker, 1 copied from upstream testdata. Only the 5 tree manifests are testkit-produced, and
  their snapshotted trees are independently pinned because golongtail built the stores from the same
  corpus. The byte gates are not self-fulfilling.
- **`build.rs` (testkit) feature gating is correct**: `cc` is an optional build-dependency
  activated only by `differential`, so a machine with no C toolchain builds and tests the pure lane
  cleanly. `-ffp-contract=off` is applied `flag_if_supported`, with an accurate comment about MSVC.

## Open questions for the maintainer

1. **Which upstream version is the intended oracle?** The submodule says `v0.3.3-101`, the dead
   download path says `v0.4.3`, the fixtures say `v0.4.5`. Answering this decides ALG-10, memo
   step 2, and whether `SeedMode::Buffer` survives.
2. **Is Windows a first-class production target?** If the Tauri app ships Windows, ALG-01 is the
   most important finding in this document and should probably block. If Windows is CI-only
   assurance for a Linux/macOS product, ALG-01 drops to P2.
3. **Was `#![cfg(unix)]` on `commands_spec.rs`, `downsync_e2e.rs`, and `smoke.rs` a deliberate
   scope decision, or did it spread from the `libc::umask` pin?** Only `lvi_byte_gate` and
   `upsync_byte_gate` have a compat reason to be unix-only (`m_Permissions`); the other three appear
   to need only mode masking, which the tree-manifest helper already supports.
4. **Should `target_chunk_size == 0` (and friends) be rejected or documented?** ALG-04 is a
   one-line fix either way, but the choice belongs to whoever owns the CLI contract with the CI
   pipeline.
5. **Is `stores/meow` worth keeping?** It is the one fixture family whose hash values nothing can
   verify, and `hash_recompute_golden` handles it with three separate `continue` arms — one of which
   is the ALG-12 hole. If meow will never be read in production, deleting the cell simplifies three
   tests.
