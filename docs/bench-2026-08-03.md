# PUT-path memory report — Rust port vs golongtail (2026-08-03)

> **Purpose.** This report backs the PUT-path memory work planned in
> [`put-path-memory.md`](put-path-memory.md). That audit's numbers were static source
> estimates; the plan made *measuring alongside the fix a prerequisite*. This is the
> measurement — a baseline that validates/corrects the estimates, plus the after-state
> for each landed optimization (P1a → P2a). The headline: the flush-path peak RSS is
> roughly **halved** and now sits **below golongtail's**, while wall time drops ~33%.

## 1. Machine spec

| item | value |
|---|---|
| CPU | Intel Core Ultra 7 155U (14 threads) |
| RAM | 30 GiB total (~9 GiB free at run time) |
| Kernel | Linux 7.1.3-200.fc44.x86_64 (Fedora) |
| rustc | 1.99.0-nightly (2026-07-06); `--release` for all measured binaries |
| golongtail | pinned **v0.4.5** (`longtail-linux-x64`, sha256 `91094c3c…`) |

Peak RSS is `wait4` `ru_maxrss` of the spawned child (KiB→MiB); wall/CPU likewise
per-child. Each cell is the median of 5 iterations.

## 2. Scenarios & methodology

Two complementary measurements, both driven by the existing e2e harness
(`support/longtail-bench/src/bin/e2e.rs`) and the CLI:

- **Flush scenario (`upsync` arm).** Pre-seed a store dir with a large synthetic
  `store_<sha>.lsi` (`write_synthetic_store_lsi`, size = `LONGTAIL_BENCH_STORE_INDEX_MB`),
  then upsync a *small delta*. The run's cost is therefore the **read → merge → flush**
  of the large store index — the OOM path from the Fellowship incident — not block I/O.
  Run at **256 MiB** index here (small enough for CI/this host; the real shard is ~1.29 GB,
  and the peak scales ~linearly with index size).
- **Large-asset scenario.** A full upsync (scan + pack) of a single **512 MiB** asset into
  a fresh store, measured with `/usr/bin/time -v`. This exercises the two whole-file-read
  vectors (scan chunker; `write_content` pack) that only the port had.

Reproduce:

```bash
# Flush scenario (Rust + golongtail, 3-way):
cargo run -p xtask -- fetch-golongtail   # once
cargo build --release -p longtail-cli
LONGTAIL_BENCH_SCENARIOS=upsync LONGTAIL_BENCH_STORE_INDEX_MB=256 \
  cargo run --release -p longtail-bench --features differential --bin e2e

# Large-asset scenario:
/usr/bin/time -v ./target/release/longtail upsync \
  --storage-uri <fresh-store> --source-path <512MiB-file-dir> \
  --target-path out.lvi --target-block-size 8388608
```

## 3. Flush scenario — before/after (256 MiB store index)

| impl / state | wall (ms) | CPU (ms) | peak RSS (MiB) | vs golongtail RSS |
|---|---|---|---|---|
| **rust — baseline** (`30b16c4`, pre-P1) | 1044 | 1019 | **843** | +57% |
| **rust — post-P1+P2a** (`c13a4d1`) | 703 | 683 | **433** | **−19%** |
| golongtail v0.4.5 | 964 | 959 | 535 | — |

**Takeaways.**
- Peak RSS **843 → 433 MiB (−49%, −410 MiB)** — roughly halved. The port went from
  **57% heavier** than golongtail to **19% lighter**.
- Wall **1044 → 703 ms (−33%)**: the memory wins are also *time* wins — dropping the
  union clone (P1a) and the doubling-realloc overshoot (P1b pre-reserve) removes real work.
- The port is now faster *and* leaner than golongtail on this path (703 vs 964 ms,
  433 vs 535 MiB).
- The audit's static ~5.2 GB flush estimate at 1.29 GB scale was for the *pre-fix* Go
  design. The measured baseline peak here is ~3.3× the index size; post-fix it is ~1.7×.
  Extrapolated to a 1.29 GB shard: baseline ≈ 4.3 GB → post-fix ≈ 2.2 GB peak — the OOM
  margin on an 8 GB host goes from "survivable, no headroom" to comfortable.

### Per-optimization progression (128 MiB index, earlier runs)

The flush peak was tracked as each P1 item landed (128 MiB synthetic index):

| state | peak RSS (MiB) | delta |
|---|---|---|
| baseline | 841 | — |
| + P1a (no union clone on GetExistingContent) | 725 | −116 (one union copy) |
| + P1b (drop `existing` before serialize; pre-reserve merge Vecs) | 466 | −259 |

P1a removes one full clone of the union index; P1b removes the transient second copy
during serialize plus the realloc overshoot from un-reserved output Vecs.

## 4. Large-asset scenario (512 MiB single asset, full upsync)

| state | peak RSS (MiB) |
|---|---|
| pre-P1c/P2a (whole-file `fs::read` on scan **and** pack) | ~512 (≈ asset size) |
| post-P1c (ranged reads in `write_content`) — pack only | ~50 |
| post-P2a (streaming scan chunker) — **full scan + pack** | **50** |

**Takeaways.**
- Both whole-file-read vectors are gone. Peak is now bounded by *one block payload*
  (~`target_block_size`) on the pack side and *one HPCDC part* (~`max_hash_size`, 32 MiB
  default) on the scan side — **independent of asset size**.
- This closes the multi-GB-pak OOM vector that was Rust-only (golongtail streams both
  paths). Multi-GB assets are in scope for this deployment, so this is load-bearing.
- **Byte-identity preserved**: the streaming chunker reads each asset one
  `max_hash_size` part at a time, and the C algorithm never lets a chunk boundary cross
  a part boundary — so the emitted chunk list is bit-identical to the whole-buffer path.
  Verified by `lvi_byte_gate` + the `upsync_byte_gate` flush gate.

## 5. Status vs the plan

- **P0** (measure + byte-compat net): done — this report + the store.lsi flush byte-gate
  (`upsync_byte_gate` GATE5) + existing `lvi_byte_gate`/`sync_fixtures`.
- **P1a/P1b/P1c**: landed and measured above.
- **P2a** (streaming scan chunker): landed; large-asset peak now asset-size-independent.
- **P2b** (full streaming `store.lsi` serializer): **not needed by the numbers.** After
  P1, the intermediate `to_bytes()` buffer is ~1× index size out of a ~1.7× peak — it no
  longer dominates, and the post-fix peak already clears the 8 GB target with headroom.
  Deferred; revisit only if a future shard size erodes the margin.
