# PUT-path memory report — Rust port vs golongtail (2026-08-03)

> **Purpose.** This report backs the PUT-path memory work planned in
> [`put-path-memory.md`](put-path-memory.md). That audit's numbers were static source
> estimates; the plan made *measuring alongside the fix a prerequisite*. This is the
> measurement — a baseline that validates/corrects the estimates, plus the after-state
> for each landed optimization (P1a → P2a). The headline: the flush-path peak RSS is
> roughly **halved** and now sits **below golongtail's**, while wall time drops ~33%.

## 1. Machine spec

| item | value |
|---|---|
| CPU | Intel Core Ultra 7 155U (14 threads) |
| RAM | 30 GiB total (~9 GiB free at run time) |
| Kernel | Linux 7.1.3-200.fc44.x86_64 (Fedora) |
| rustc | 1.99.0-nightly (2026-07-06); `--release` for all measured binaries |
| golongtail | pinned **v0.4.5** (`longtail-linux-x64`, sha256 `91094c3c…`) |

Peak RSS is `wait4` `ru_maxrss` of the spawned child (KiB→MiB); wall/CPU likewise
per-child. Each cell is the median of 5 iterations.

## 2. Scenarios & methodology

Two complementary measurements, both driven by the existing e2e harness
(`support/longtail-bench/src/bin/e2e.rs`) and the CLI:

- **Flush scenario (`upsync` arm).** Pre-seed a store dir with a large synthetic
  `store_<sha>.lsi` (`write_synthetic_store_lsi`, size = `LONGTAIL_BENCH_STORE_INDEX_MB`),
  then upsync a *small delta*. The run's cost is therefore the **read → merge → flush**
  of the large store index — the OOM path from the Fellowship incident — not block I/O.
  Run at **256 MiB** index here (small enough for CI/this host; the real shard is ~1.29 GB,
  and the peak scales ~linearly with index size).
- **Large-asset scenario.** A full upsync (scan + pack) of a single **512 MiB** asset into
  a fresh store, measured with `/usr/bin/time -v`. This exercises the two whole-file-read
  vectors (scan chunker; `write_content` pack) that only the port had.

Reproduce:

```bash
# Flush scenario (Rust + golongtail, 3-way):
cargo run -p xtask -- fetch-golongtail   # once
cargo build --release -p longtail-cli
LONGTAIL_BENCH_SCENARIOS=upsync LONGTAIL_BENCH_STORE_INDEX_MB=256 \
  cargo run --release -p longtail-bench --features differential --bin e2e

# Large-asset scenario:
/usr/bin/time -v ./target/release/longtail upsync \
  --storage-uri <fresh-store> --source-path <512MiB-file-dir> \
  --target-path out.lvi --target-block-size 8388608
```

## 3. Flush scenario — before/after (256 MiB store index)

Peak RSS (`ru_maxrss`) is stable run-to-run; wall/CPU on this laptop swing ~20% with
ambient load, so read wall *relative to the golongtail leg measured in the same
invocation*, not across rows. Each rust state was measured against its own golongtail run.

| impl / state | wall (ms) | CPU (ms) | peak RSS (MiB) | vs golongtail RSS |
|---|---|---|---|---|
| **rust — baseline** (`30b16c4`, pre-P1) | 1044 | 1019 | **843** | +57% |
| **rust — post-P1+P2a** (`c13a4d1`) | 703 | 683 | **433** | −19% |
| **rust — post-Bytes-I/O** (owned-`Bytes` blob write) | 864 | 845 | **305** | **−43%** |
| golongtail v0.4.5 (same-run range) | 964–1164 | 959–1177 | 535 | — |

**Takeaways.**
- Peak RSS **843 → 433 → 305 MiB (−64% total, −538 MiB)**. The port went from **57%
  heavier** than golongtail on this path to **43% lighter** (305 vs 535 MiB).
- The Bytes-I/O step (owned-`Bytes` blob write; see §5) removed the fs write path's
  `to_vec()` copy of the serialized index — one full index-sized buffer — for the
  433 → 305 drop. On S3 the same change removes *two* more copies the fs bench can't
  exercise (the `put_object` body `to_vec` and one of the two GET-read copies), so the
  real-backend win is larger than this fs number shows.
- Wall stays parity-or-better vs golongtail every step (e.g. 864 vs 1164 ms in the final
  run — ~26% faster; the earlier absolute numbers differ only by ambient load).
- The audit's static ~5.2 GB flush estimate at 1.29 GB scale was for the *pre-fix* Go
  design. The measured baseline peak here is ~3.3× the index size; post-fix it is ~1.2×.
  Extrapolated to a 1.29 GB shard: baseline ≈ 4.3 GB → post-fix ≈ 1.5 GB peak — the OOM
  margin on an 8 GB host goes from "survivable, no headroom" to comfortable.

### Per-optimization progression (128 MiB index, earlier runs)

The flush peak was tracked as each P1 item landed (128 MiB synthetic index):

| state | peak RSS (MiB) | delta |
|---|---|---|
| baseline | 841 | — |
| + P1a (no union clone on GetExistingContent) | 725 | −116 (one union copy) |
| + P1b (drop `existing` before serialize; pre-reserve merge Vecs) | 466 | −259 |

P1a removes one full clone of the union index; P1b removes the transient second copy
during serialize plus the realloc overshoot from un-reserved output Vecs.

## 4. Large-asset scenario (512 MiB single asset, full upsync)

| state | peak RSS (MiB) |
|---|---|
| pre-P1c/P2a (whole-file `fs::read` on scan **and** pack) | ~512 (≈ asset size) |
| post-P1c (ranged reads in `write_content`) — pack only | ~50 |
| post-P2a (streaming scan chunker) — **full scan + pack** | **50** |

**Takeaways.**
- Both whole-file-read vectors are gone. Peak is now bounded by *one block payload*
  (~`target_block_size`) on the pack side and *one HPCDC part* (~`max_hash_size`, 32 MiB
  default) on the scan side — **independent of asset size**.
- This closes the multi-GB-pak OOM vector that was Rust-only (golongtail streams both
  paths). Multi-GB assets are in scope for this deployment, so this is load-bearing.
- **Byte-identity preserved**: the streaming chunker reads each asset one
  `max_hash_size` part at a time, and the C algorithm never lets a chunk boundary cross
  a part boundary — so the emitted chunk list is bit-identical to the whole-buffer path.
  Verified by `lvi_byte_gate` + the `upsync_byte_gate` flush gate.

## 5. Download-path follow-up — preflight union clone (finding 6)

The same fable review flagged the **download** analogue of P1a. `preflight_get`
(`remote.rs`) sized its prefetch permits by calling `get_index_snapshot()`, which routes
through the index owner's `GetIndex` → `merged_index` → **`base.clone()`** — a full copy
of the union store index — and then built a `size_by_hash` map over **every block in the
store**. It only needs Σ chunk_sizes for the *requested* working set.

Fix: a dedicated `IndexCommand::GetBlockSizes` served by a new
`StoreIndex::block_payload_sizes(&wanted)` (longtail-core) that sums chunk sizes straight
from the packed arrays for only the requested hashes — no `BlockIndex` materialization, no
union clone, and a result map bounded by the working set rather than the whole store. On a
cold `get` without a version-local store-index override (**the Tauri download path**), the
old code allocated a full copy of a multi-GB union on end-user machines per preflight; that
allocation is now gone.

**Measurement gap (honest):** the existing download scenarios (cold/warm/incremental) use a
*small* store index, so they don't exercise the win (which scales with union size vs.
working-set size). A hard RSS number needs a new "download a small delta against a large
store index" scenario — not yet built. The change is proven structurally (the `base.clone()`
is removed) and by unit tests (`block_payload_sizes_*` in `store_algebra.rs`) plus the
`prefetch_budget` suite that exercises `preflight_get`'s permit sizing.

## 6. Read-path union merge — consuming merge (finding 7)

A real-S3 `validate-version` comparison on a month-end production shard (2×1.29 GB store
index) showed the pure-Rust read path already **below** golongtail on peak RSS — rust
~5.6 GB median vs go ~6.4 GB, and rust's *worst* run beat go's *best*. But 5–6 GB on an
8 GB host is still tight, and the driver is the two-shard union merge in
`merge_store_index_items`: `acc = existing.merge(&tmp)` holds `existing + tmp + a fresh
output` — ~3 shards — at the peak.

Fix: `StoreIndex::merge_consuming(self, other)` (longtail-core). Merge Pass 1 copies
`local`'s unique blocks in order, re-deriving cumulative offsets — so when `local` is
already canonical and free of internal duplicate block hashes (always true for a shard
parsed from a valid `.lsi`), that output is **bit-identical to `local` itself**. So the
consuming merge keeps `self` and only appends Pass 2 (remote-only blocks), dropping the
peak from `local + remote + output` (~3 shards) to `output + remote` (~2). Non-canonical /
duplicate inputs fall back to the allocating `merge` for an exact result. Wired into the
read/union path (`merge_store_index_items`) and both flush paths (`try_add`,
`try_add_with_locking`).

**Byte-identity** is load-bearing (shard name = sha256 of these bytes) and proven: two
proptests assert `merge_consuming` bytes == `merge` bytes over canonical *and* arbitrary
(fallback + error-path) inputs, plus targeted unit tests; `sync_fixtures` (shard-name
sha256) and the upsync byte gates pass.

**Measured** with a pure, network-free micro-bench (`longtail-bench --bin merge_mem`) that
merges two distinct canonical 332 MiB/shard indexes:

| mode | peak RSS | union output |
|---|---|---|
| `merge` (allocating) | **1401 MiB** | 6,000,000 blocks, hashsum `0x2536…d59c` |
| `merge_consuming` | **1069 MiB** | 6,000,000 blocks, hashsum `0x2536…d59c` |

**−331 MiB (−24%)** — precisely one shard, exactly as predicted; the identical block count
*and* hashsum confirm byte-identical output. Extrapolated to the 2×1.29 GB production month,
that is **~1.3 GB off the read/union peak** (the `validate-version` peak moves from ~5.6 GB
toward ~4.3 GB). On the flush paths it removes the pre-merge union copy too, though there
the `to_bytes()` buffer still co-dominates.

## 7. Status vs the plan

- **P0** (measure + byte-compat net): done — this report + the store.lsi flush byte-gate
  (`upsync_byte_gate` GATE5) + existing `lvi_byte_gate`/`sync_fixtures`.
- **P1a/P1b/P1c**: landed and measured above.
- **P2a** (streaming scan chunker): landed; large-asset peak now asset-size-independent.
- **Bytes-I/O follow-up** (from a fable review of the landed work): `BlobObject::write`
  now takes an owned `bytes::Bytes` instead of `&[u8]`, so the serialized index/block
  payload moves into the S3 `ByteStream` / fs `spawn_blocking` closure with no copy, and
  the put-retry loop reclones for O(1). The S3 GET path also collapses a
  `into_bytes().to_vec()` double-copy to a single `to_vec()`. `write_to_uri` (the facade
  `.lvi`/version-local-`.lsi`/prune writes) takes `Bytes` end-to-end for the same reason.
  This is what took the fs flush peak 433 → 305 MiB; it removes more on S3.
- **P2b** (full streaming `store.lsi` serializer): **not needed by the numbers.** With the
  Bytes-I/O copies gone, the remaining peak is the live `StoreIndex` + one `to_bytes()`
  buffer (~1.2× index). A streaming serializer would shave part of that lone buffer, but
  it is genuinely hard here — the shard key *is* `sha256(to_bytes())`, so it needs a
  two-pass hash-then-stream plus a sized streaming S3 body, not just a serializer — and
  the post-fix ~1.5 GB extrapolated peak already clears 8 GB with room. Deferred; revisit
  only if a future shard size erodes the margin.
